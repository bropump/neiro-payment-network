# Set up an operator for the user

Carry the setup through to a working, verified operator. Use the user's chosen host and existing permissions; ask only for missing host access, signer choice, fee settings or funding limits. An agent performs the steps below using normal build, file and service tools. This guide is not an automatic installer, and the publisher itself only administers the listing.

Establish whether the user wants a test or an operating public provider before publication. Existing test endpoints must not be promoted to production by assumption. For tests, close created listings after verification unless the user explicitly asks to retain them. A retained test listing remains publicly discoverable; the current record format has no production-certification field.

Follow this page in order. [Publication](REGISTRATION.md) creates one listing per operator under the existing SPL Record program. There is no shared directory account to initialize and no central registration service to join.

1. **Install on the chosen host.** Inspect its existing tools and follow [official Kora deployment instructions](https://solana.com/docs/tools/kora/operators). Reuse an official, successfully built Kora release and record its pin; do not patch Kora or its SDK. Install Node.js 24 or later for the listing runner. From this repository run:

   ```sh
   cd tools/kora-publisher/script
   npm ci --ignore-scripts --registry=https://registry.npmjs.org
   node runner.mjs --help
   ```

   The runner needs no Rust compiler, native build or custom installer. The existing Rust publisher is an optional reference. Keep the script and its locked dependencies together. Use the absolute path to `runner.mjs` in private service commands. Docker is optional.

2. **Configure where signing happens.** Reuse the user's operator signer or provision an operator-controlled signer when authorized. Configure the local or remote Keychain backend in private `signers.toml`, and supply its credentials through the host's private environment/secret storage. Both Kora and the publisher must resolve the same public operator key. Preserve the user's access to the signer and its recovery material; never print or publish keys. The Node adapter supports the official Keychain memory, Turnkey, Privy, Vault and Openfort packages using the existing Kora environment references. Tests cover the five mappings; live signer evidence is limited to memory, so do not claim remote deployment integration. Nonempty custom `http_config` is rejected because the published JS factories cannot preserve it; remote factory/signing operations have a 30-second caller deadline. For Vault, the pinned Rust schema requires `vault_addr_env` and `vault_token_env`, despite different names in its upstream example. See [signer choices](SIGNING.md).

3. **Prepare configuration and funding.** Copy the [Kora config](../examples/operator/kora.toml) and [signer template](../examples/operator/signers.toml) into one private deployment directory, preserving existing settings when updating an operator. Apply the user's fees and spending limits; keep signer funds protected by the appropriate fee-payer policies. Set `SOLANA_RPC_URL` for the runner and configure Kora's mainnet RPC, Jupiter credentials and the operator's public HTTPS endpoint using the host's normal tools. Check the operator's SOL for fees, listing rent and intended sponsorship, and prepare its NEIRO fee-receipt account. Check that the separately authorized test payer has NEIRO. There is no fixed NEIRO deposit required by an SPL listing. Reuse existing token accounts and fund only within the user's authorization.

4. **Derive and block the listing before publishing.** Run the command below with the operator's actual public key. It needs no signing credentials and creates no account. This is the listing address, not the operator wallet address. Add the printed address to the existing `[validation].disallowed_accounts` array in the private `kora.toml`, preserving other entries. Do not block the entire SPL Record program or add a duplicate TOML section. Apply that same deny entry to every public Kora instance sharing the signer. This is the agent's configuration-editing step; the publisher does not edit Kora's config itself.

   ```sh
   node /ABS/tools/kora-publisher/script/runner.mjs address --operator OPERATOR_PUBLIC_KEY
   ```

5. **Start Kora and verify the loaded settings.** Start or restart stock Kora using the private configuration and existing service manager. Check its HTTPS endpoint's `getConfig` and `getPayerSigner`: expected operator, payment destination, fee terms, NEIRO acceptance and listing deny address must match. Keep authentication and other protections intact; report unsupported integration requirements instead of weakening them to force a pass.

6. **Sign and publish the terms.** From the private deployment directory, with the same signer environment available, run:

   ```sh
   node /ABS/tools/kora-publisher/script/runner.mjs publish --operator OPERATOR_PUBLIC_KEY --url https://OPERATOR_HOST/ --config /PRIVATE/kora.toml --signers-config /PRIVATE/signers.toml --state-dir /PRIVATE/renewal
   ```

   Replace the placeholders with the verified public key and endpoint. Use `--config` and `--signers-config` if the files are elsewhere, and `--signer-name` if multiple signers are configured. The publisher checks the responding server, automatically serializes the ten v5 fields including the finalized block slot and hash, signs the bound terms directly through Keychain and submits through Solana RPC. This same command creates new listings and migrates existing v1/v2/v3/v4 listings; operators do not manually construct the payload or perform separate manual signing. Confirm the saved transaction signature and read the finalized record back. Use one private mode-0700 state directory for publication, renewal and closure. The runner writes `pending.json` before submission and preserves a `finalized.json` slot floor during reconciliation. On timeout, retain that state and reconcile the saved signature; never switch directories to bypass an unresolved send. Before migrating from a Rust worker, disable it and verify all old worker processes are stopped before Node uses the same persistent state.

7. **Verify protection, discovery and a payment.** Check enabled public signing methods reject bounded, non-destructive requests touching the listing for the actual account-deny reason; a disabled method or authentication error is not that proof. Use a separate client to scan SPL Record for the `NEIRO069` listing format, authenticate record ownership, authority, derived address and the separate operator signature using the [signed format and reproducible verification command](../tools/kora-publisher/client/README.md#reproduce-the-live-bunny-signature-check), read the operator's SOL, and request a quote directly from its listed URL. Verify the live configuration and independently calculated fee against the listing, then check the exact payment message before any authorized signing. The Node runner provides `discover` for strict v5 RPC discovery and `check` for a no-send comparison against live configuration; independent quote and exact-transaction verification remain client responsibilities. Run a tiny real payment only within the user's already authorized recipient/amount/fee limits, check finality and balance changes, and return test funds as requested. Close only accounts created for the test when eligible; never close pre-existing ATAs. A quote or simulation alone is not a completed payment.

8. **Enable required renewal.** Follow [renewal scheduling](RENEWAL.md) to supervise `node /ABS/tools/kora-publisher/script/runner.mjs renew --operator OPERATOR_PUBLIC_KEY --url https://OPERATOR_HOST/ --config /PRIVATE/kora.toml --signers-config /PRIVATE/signers.toml --state-dir /PRIVATE/renewal --watch`, or invoke the same command without `--watch` from an hourly native timer. Use the same operator, configuration and signer environment. Run one worker per signer across all hosts. The worker checks finalized chain time and renews unchanged terms only after 24 hours; clients reject them at 48 hours from their finalized block anchor. Preserve the state directory and reconcile pending submissions rather than discarding journals. A crash may leave `runner.lock`; it never expires based on the host clock. Remove it only after verifying the old process is dead, while retaining and reconciling pending and finalized state. Confirm the first run and record service/timer status, logs and stop commands.

Finish with one short private operating note: Kora/Node versions and runner revision, config paths, public signer/listing/endpoint, signature receipts, funding and fee totals, passed checks, unresolved gaps, and host-specific start/restart/stop commands. Never include secrets. Keep an operational listing open; close it only when the user wants a temporary test cleaned up or the operator retired.

## Later changes

- **Upgrade an existing listing:** install the current runner's locked dependencies and run the same `publish` command with the existing private state directory after stopping old workers. This rewrites the old listing in place with the v5 terms, finalized block anchor and signature. Preserve its address, authority, rent and deny entry. Legacy listings are rejected until migrated. Current v5 terms send nothing until the 24-hour renewal threshold; changed terms update immediately. An operator must authorize their own update; installing new reader code cannot remotely migrate another operator’s record.

- **Change fees:** update private Kora config, restart all relevant instances, verify the running terms, then run `publish` again with the same private state directory, coordinated with the sole renewal worker. The listing address and deny entry stay the same. Unchanged terms younger than 24 chain hours send no transaction. Clients must reject stale/mismatched terms during the update window.
- **Retire:** disable the renewal worker and wait for any active run to finish; reconcile pending submissions, then run `node /ABS/tools/kora-publisher/script/runner.mjs close --operator OPERATOR_PUBLIC_KEY --signers-config /PRIVATE/signers.toml --state-dir /PRIVATE/renewal`, verify finalized closure and recovered rent, then remove the deny entry only if it is no longer needed. Retaining it protects future recreation at the same address.
- **Operate:** use the host's normal restart, monitoring and update tools. Preserve signer identity and deny entries across upgrades. Confirm settings and rejection behavior again after changes; arrange ongoing automation only within the user's requested scope.

See [listing details and the Mac/Bunny deny snippets](SPL-RECORD-LISTINGS.md). The historical Rust publication, direct-client quote/payment and cleanup flow passed the documented Mac/Bunny mainnet test; those receipts are not evidence that a Node worker has been deployed there. This guide does not certify a new host, every signer backend or protection across unobserved instances; verify each actual deployment.
