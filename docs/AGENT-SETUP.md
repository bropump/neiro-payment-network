# Set up an operator for the user

Carry the setup through to a working, verified operator. Use the user's chosen host and existing permissions; ask only for missing host access, signer choice, fee settings or funding limits. An agent performs the steps below using normal build, file and service tools. This guide is not an automatic installer, and the publisher itself only administers the listing.

Establish whether the user wants a test or an operating public provider before publication. Existing test endpoints must not be promoted to production by assumption. For tests, close created listings after verification unless the user explicitly asks to retain them. A retained test listing remains publicly discoverable; the current record format has no production-certification field.

Follow this page in order. [Publication](REGISTRATION.md) creates one listing per operator under the existing SPL Record program. There is no shared directory account to initialize and no central registration service to join.

1. **Build on the chosen host.** Inspect its existing tools and follow [official Kora deployment instructions](https://solana.com/docs/tools/kora/operators). Use an official, successfully built Kora revision and record the pin; do not patch Kora or its SDK. From its source checkout, build `cargo build --release --locked --bin kora`. From this repository's `tools/kora-publisher`, build `cargo build --release --locked`. Put the resulting executables on that host's executable path. Reuse an existing compatible stock Kora installation. Native build prerequisites follow upstream; do not introduce a custom installer or require Docker unless the host needs it.

2. **Configure where signing happens.** Reuse the user's operator signer or provision an operator-controlled signer when authorized. Configure the local or remote Keychain backend in private `signers.toml`, and supply its credentials through the host's private environment/secret storage. Both Kora and the publisher must resolve the same public operator key. Preserve the user's access to the signer and its recovery material; never print or publish keys. The publisher currently requires a compatible raw-message signing backend; do not promise every Kora signer type works. See [signer choices](SIGNING.md).

3. **Prepare configuration and funding.** Copy the [Kora config](../examples/operator/kora.toml) and [signer template](../examples/operator/signers.toml) into one private deployment directory, preserving existing settings when updating an operator. Apply the user's fees and spending limits; keep signer funds protected by the appropriate fee-payer policies. Configure mainnet Solana RPC, Jupiter credentials and the operator's public HTTPS endpoint using the host's normal tools. Check the operator's SOL for fees, listing rent and intended sponsorship, and prepare its NEIRO fee-receipt account. Check that the separately authorized test payer has NEIRO. There is no fixed NEIRO deposit required by an SPL listing. Reuse existing token accounts and fund only within the user's authorization.

4. **Derive and block the listing before publishing.** Run the command below with the operator's actual public key. It needs no signing credentials and creates no account. This is the listing address, not the operator wallet address. Add the printed address to the existing `[validation].disallowed_accounts` array in the private `kora.toml`, preserving other entries. Do not block the entire SPL Record program or add a duplicate TOML section. Apply that same deny entry to every public Kora instance sharing the signer. This is the agent's configuration-editing step; the publisher does not edit Kora's config itself.

   ```sh
   neiro-kora-publisher --operator OPERATOR_PUBLIC_KEY address
   ```

5. **Start Kora and verify the loaded settings.** Start or restart stock Kora using the private configuration and existing service manager. Check its HTTPS endpoint's `getConfig` and `getPayerSigner`: expected operator, payment destination, fee terms, NEIRO acceptance and listing deny address must match. Keep authentication and other protections intact; report unsupported integration requirements instead of weakening them to force a pass.

6. **Sign and publish the terms.** From the private deployment directory, with the same signer environment available, run:

   ```sh
   neiro-kora-publisher --operator OPERATOR_PUBLIC_KEY publish --url https://OPERATOR_HOST/ --journal listing-create.json
   ```

   Replace the placeholders with the verified public key and endpoint. Use `--config` and `--signers-config` if the files are elsewhere, and `--signer-name` if multiple signers are configured. The publisher checks the responding server, automatically serializes the ten v5 fields including the finalized block slot and hash, signs the bound terms directly through Keychain and submits through Solana RPC. This same command creates new listings and migrates existing v1/v2/v3/v4 listings; operators do not manually construct the payload or perform separate manual signing. Confirm the saved transaction signature and read the finalized record back. On timeout, reconcile the journaled signature before retrying; do not blindly repeat with a new journal.

7. **Verify protection, discovery and a payment.** Check enabled public signing methods reject bounded, non-destructive requests touching the listing for the actual account-deny reason; a disabled method or authentication error is not that proof. Use a separate client to scan SPL Record for the `NEIRO069` listing format, authenticate record ownership, authority, derived address and the separate operator signature using the [signed format and reproducible verification command](../tools/kora-publisher/client/README.md#reproduce-the-live-bunny-signature-check), read the operator's SOL, and request a quote directly from its listed URL. Verify the live configuration and independently calculated fee against the listing, then check the exact payment message before any authorized signing. Discovery is client-side code, not a publisher command. Run a tiny real payment only within the user's already authorized recipient/amount/fee limits, check finality and balance changes, and return test funds as requested. Close only accounts created for the test when eligible; never close pre-existing ATAs. A quote or simulation alone is not a completed payment.

8. **Enable required renewal.** Follow [renewal scheduling](RENEWAL.md) to invoke `renew --url https://OPERATOR_HOST/ --state-dir /PRIVATE/PERSISTENT/PATH` hourly using the host's normal service manager. Use the same operator, configuration and signer environment. Run one worker per signer across all hosts. The worker checks finalized chain time and renews unchanged terms only after 24 hours; clients reject them at 48 hours from their finalized block anchor. Preserve the state directory and reconcile pending submissions rather than discarding journals. Confirm the first run and record timer status, logs and stop commands.

Finish with one short private operating note: binary versions, config paths, public signer/listing/endpoint, signature receipts, funding and fee totals, passed checks, unresolved gaps, and host-specific start/restart/stop commands. Never include secrets. Keep an operational listing open; close it only when the user wants a temporary test cleaned up or the operator retired.

## Later changes

- **Upgrade an existing listing:** build the current publisher and run the same `publish` command with a fresh journal. This rewrites the old listing in place with the v5 terms, finalized block anchor and signature. Preserve its address, authority, rent and deny entry. Legacy listings are rejected until migrated. Current v5 terms send nothing until the 24-hour renewal threshold; changed terms update immediately. An operator must authorize their own update; installing new reader code cannot remotely migrate another operator’s record.

- **Change fees:** update private Kora config, restart all relevant instances, verify the running terms, then run `publish` again with a fresh journal path. The listing address and deny entry stay the same. Unchanged terms younger than 24 chain hours send no transaction. Clients must reject stale/mismatched terms during the update window.
- **Retire:** disable the renewal worker and wait for any active run to finish; reconcile pending submissions, then run `neiro-kora-publisher --operator OPERATOR_PUBLIC_KEY close --journal listing-close.json`, verify finalized closure and recovered rent, then remove the deny entry only if it is no longer needed. Retaining it protects future recreation at the same address.
- **Operate:** use the host's normal restart, monitoring and update tools. Preserve signer identity and deny entries across upgrades. Confirm settings and rejection behavior again after changes; arrange ongoing automation only within the user's requested scope.

See [listing details and the Mac/Bunny deny snippets](SPL-RECORD-LISTINGS.md). The publication, direct-client quote/payment and cleanup flow passed the documented Mac/Bunny mainnet test. This guide does not certify a new host, every signer backend or protection across unobserved instances; verify each actual deployment.
